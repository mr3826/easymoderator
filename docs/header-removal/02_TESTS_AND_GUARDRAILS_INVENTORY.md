## Summary
Mapped the full header presentation/governance surface for the page-level signal-header removal (READ-ONLY, no edits). The permanent header anatomy lives in `dashboard/PageHeader.tsx` (breadcrumb → h1 title → `SignalBadge` carrying the per-page `signalTestId` → `whyHere` subtitle → `ActionBar` primary/secondary with default `dashboard-primary-action` testid), consumed by every merchant page via a stable set of signal testids: dashboard-signal, inbox-signal, orders-signal, products-signal, customers-signal, payment-signal, billing-signal, notification-signal, channels-signal, automation-signal, business-signal, faq-signal, policies-signal, delivery-signal, plus record-level rto-signal/customer-state. Across ~22 Playwright specs and ~12 Vitest guardrail suites there is ONE uniform 'execution header'/'Core Design Test' pattern — `<h1 title> + <page-signal> containsText <label> + dashboard-primary-action toHaveCount(0)/toBeNull` — and only three things genuinely need to FLIP: (a) the `<page>-signal` CONTAINS-TEXT line (relocate to the contextual indicator, never delete), and (b) the dashboard/inbox DOM-band + bounding-box pins, while everything else (payload/CSRF/retry/focus-trap/390/360/200% overflow/axe/PII-free/state-honesty, the no-header-CTA absence guards, and the record-level + degraded/blocked status indicators) is functional/safety coverage that MUST be preserved. The guardrails doc §5.2 (overview anatomy), §21.1 (L893), §25 L1281 (scoped only to Orders/Inbox), and §29 L1407/L1411 (dashboard "not useful signals") are the exact lines that mandate a permanent overview signal header and must be amended; §4/§8/§22/§23/§24 already prohibit it for execution pages and give the extension basis. No pixel-diff visual-regression baseline exists (ad-hoc fullPage screenshots only), so removal breaks no image test but the before/after evidence should be regenerated. Highest-impact traps: header signal testids are widely reused as page-mounted readiness gates (removal causes unrelated-looking timeout/flakes), and signal/whyHere i18n keys stay referenced by derive()/derive.test.ts so they are NOT safe to bulk-delete.
