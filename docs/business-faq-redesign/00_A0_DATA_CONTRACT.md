## A5 contract — FAQ API (knowledge.routes/controller/service/validator)

New responses: every FAQ serialization exposes `id, question, category_tag, answers {en,bn}, keywords, notes, status, is_active (mirror), priority, use_count, created_at, updated_at, sync_status, sync_version, synced_at`. `use_count` labeled as **replies used** (not retrieval; not success).
Transitions: PATCH status (validated machine), POST `/:id/archive`, `/:id/restore` (restore→previous disabled state: store nothing extra — restore to 'disabled'), POST `/:id/resync` (owner) → sets pending + version++ + triggers sync, returns fresh row. DELETE remains hard delete (owner) + deletePoint.
Sync integrity (mission §6, all inside knowledge.service + rag touchpoints):
- Save = DB tx commit first; on success sync_status='pending', sync_version+=1; then fire async syncFaqRagIndex (never blocks response, never throws to caller); success → 'synced'+synced_at; failure → 'failed' (visible, retryable). **API responses distinguish saved vs synchronized; UI must too.**
- Write-side version guard: Qdrant point payload gains `faq_version`; sync/ingest refuses to overwrite a point whose stored faq_version > current row's (stale async cannot clobber newer content); delete uses scoped point id as today.
