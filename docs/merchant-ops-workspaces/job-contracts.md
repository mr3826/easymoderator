# Orders and Customers Job Contracts

**Mission:** `merchant-ops-workspaces-2026-11-02`
**Source baseline:** `ab0c958efab03a0214776bdb07c95537eaae828c`
**Scope:** Bangladesh-only merchant web application. These are source-backed contracts and test hypotheses, not field-research claims.

## Evidence and decision method

The discovery used four complementary passes: source-to-API/state tracing (A1), job-first desktop/mobile review (A2), BD commercial and false-positive challenge (A3), and tenant/identity/security review (A4). A8 independently mapped acceptance tests before implementation. The project V6 persona pack itself states that its merchant psychology and UX roles are working/simulated adaptations; no merchant interviews or observed time-on-task results are available. Do not report market validation, representative BD behavior, or measured time savings from these reviews.

Design alternatives:

| Option | Merchant value | Cost and failure risk | Decision |
|---|---|---|---|
| A. Cosmetic compression of existing dashboard cards | Recovers some space but leaves the merchant scanning non-actionable summaries and duplicated status controls. | Lowest code cost; preserves untrusted counts, mixed lifecycle/payment semantics, and delayed first action. | Reject as the complete solution; reuse only compact visual treatment. |
| B. Task-centered list with supported filters and selected-record context | Search, inspect, take the next permitted action, and understand its result without losing queue position. Counts are absent unless tied to an authoritative matching query. | Moderate component work; depends on preserving API truth, permissions, and responsive details. | Select. It best matches the request and existing table/detail APIs without inventing a workflow engine. |

## Merchant jobs and action contracts

`Owner` means an existing shop owner/admin authority; it does not create a new role. `Moderator` means an existing account/permission in the repository. `Packing/dispatch staff` is a task persona only: no dedicated packer role exists, so controls must follow actual shop membership/permission and server authorization.

| Actor / trigger | Required data and authority | Allowed action and state transition | Result proof, next action, and recovery |
|---|---|---|---|
| Owner, moderator, or authorized dispatch member opens Orders to find an order by ID, customer, or phone. | `GET /api/order` (authenticated, active shop membership); server supports order number, customer name, and phone search, page/limit, and newest-first ordering. It returns an array without a total/`has_more`; the UI currently requests page 1, limit 100. It does not search channel. | Search/filter the server-backed list. Default to `All Orders`; do not invent a server-backed `Needs Action` queue or whole-shop KPI. Keep filters as separate order, delivery, payment, and date facts where supported. | Show the exact returned rows, visible scope/pagination, loading, empty-shop, no-match and request-error states. On refresh failure, do not silently present stale rows as current. Retry without losing the query. Search copy must only promise supported fields. |
| Authorized operator inspects an order before confirmation or handoff. | `GET /api/order/:id`; order fields, line items, address, amounts, payment status, delivery history, and Customer 360 link are separate authorities. Confidence decision is `GET /api/order-confidence/orders/:orderId`. | Open contextual details without losing the list position. Explain risk evidence as a phone/order signal with uncertainty, not a person-level verdict. A phone match is provisional and read-only. | Show source, current state, unknown/stale state, and exact customer/order ID. If detail or confidence lookup fails, show unavailable/retry, not clear/low risk. Return to the same list query. |
| Operator creates a manual order. | Existing authenticated shop order-create flow (`POST /api/order/draft` or REST create path selected by current client); server validates shop scope and order fields. Frontend currently sends an idempotency key. | Create the supported draft and show the actual created order ID. A phone/RTO signal must not automatically decline the buyer. Do not invent `customer_id` from name/phone or report payment/delivery as complete. | Show create success only after the returned record exists; preserve the idempotency key across safe retries. Surface validation, permission, timeout/unknown-result and conflict distinctly; allow lookup by returned/existing order ID before retrying an unknown result. |
| Operator confirms an eligible order. | `POST /api/order/:orderId/confirm`; order state, stock/address/customer facts, and the existing order-confidence workflow. Confidence verify is `POST /api/order-confidence/orders/:orderId/verify`; manual-review approval is `POST .../:orderId/approve` and owner/admin only. | Present only the next safe action for the current state and the signed-in user's actual permissions. A confirmation means confirmed, not delivered or settled. `VERIFY` and `MANUAL_REVIEW` remain distinct. | Confirm with the server-returned status and any audit/error detail; refresh the row and panel from the authority. A 403/409/422 or timeout must not produce a success toast or optimistic final status; retain context and offer a safe retry/review. |
| Authorized dispatch member books a courier for an eligible confirmed/processing order. | `POST /api/order/:orderId/courier` (canonical booking boundary); provider account, address, phone, line items, and authoritative COD amount; server-side confidence gate runs before provider booking. Existing providers are Pathao, Steadfast, and RedX. | Book one item at a time only when server and provider requirements pass. Do not add bulk status/dispatch actions. Never equate booking with handoff, delivery, or collection. | Show provider, tracking ID, and actual booking status from the response. On 409/timeout/ambiguous provider result, query the order/claim before retry; do not create duplicate bookings. If `partially_paid` has no authoritative due amount, block booking with an explanation rather than sending full order total as COD. |
| Owner/reviewer or authorized shop member encounters an order risk signal. | Order Confidence source, reason-coded decision and evidence. RTO check is `POST /api/rto-shield/check`; its authenticated endpoint currently accepts a free-form phone and can reveal global blacklist evidence, so the redesigned UI must only use an in-shop order/customer context. | Verification of `VERIFY` may be recorded by an existing shop role; `MANUAL_REVIEW` approval is owner/admin only and requires the existing reason. A phone signal is not identity proof and must never auto-decline a buyer. | Show the underlying phone/order facts, source, stale/ambiguous uncertainty, and permitted human review. Server 403/409/conflicts remain authoritative. No fabricated fraud probability, global blacklist editor, or arbitrary-phone search. |
| Owner/admin searches Customers by contact, name, or verified relationship. | Legacy `GET /api/customer` returns page metadata; `search` currently filters name only, while phone/email are separate filters. Customer 360 is feature-gated and uses exact `customer_id` first; unlinked orders can be read-time `PHONE_MATCH`. | Support contact lookup using the actual API contract. If search is consolidated to OR across fields, validate/parameterize it and test without changing tenant scope. Do not infer purchase from a Messenger contact. | Label contact/profile vs. confirmed order relationship. Distinguish no customers, no matches, loading, access denied, missing detail, unavailable relationship data, and partial API failure. Retry without clearing the search. |
| Operator opens a customer profile from the list or a verified conversation/order deep link. | Customer 360/read APIs and current pilot flag; exact `customer_id` association is verified. Phone-only match is provisional and may be ambiguous/shared. Customer 360 history is capped and not paginated. | Show exact-ID history separately from possible phone matches. Do not merge, persist a phone match, attribute another profile's orders as verified buyer history, or compute repeat-buyer/risk/value claims from ambiguous matches. | Link to an exact verified order or conversation when the relationship is authoritative. Label provisional matches and their limits. On stale/missing/ambiguous data, show that state and a safe verification suggestion; do not imply a completed identity merge. |
| Owner/staff uses notes or tags to preserve service context. | Existing shop-scoped customer notes/tags APIs are implemented in Inbox context, not Customer 360. Notes are team-visible despite older “private” wording; author/owner/admin mutation rules apply. | Connect existing note/tag actions only if the selected profile has an authoritative customer ID and current API permissions. Do not add promotional messaging or automatic follow-up. | Show saved content only after server success; honor 403/404/409 and refresh state. Label notes as team-visible, not private. If the feature is not connected in this slice, link back to the supported Inbox action rather than displaying dead controls. |
| Owner/admin opens risk-network participation settings. | `GET/PUT /api/rto-shield/settings`; server currently stores `contribute` and `enforce`, but delivery ingestion and network aggregation do not fully honor `contribute=false`; read failure is incorrectly rendered as both toggles `true`; settings routes currently use membership, not owner/admin consent authorization. | Keep configuration secondary and discoverable. Before displaying “opt out” as effective, fix server ingestion and aggregation, prior-stat treatment, consent role and audit behavior. A failed settings read is `unavailable`, never an assumed enabled/disabled choice. | Show saved server state and clear save/revert status. Deny unauthorized participation changes server-side; audit consent changes. If unavailable, disable toggles and give a retry path without asserting a value. |
| Owner/admin adds or deletes a customer. | Existing customer create/delete APIs are shop-scoped; delete is owner/admin server-enforced. Customer deletion does not establish complete erasure of all phone-keyed RTO evidence or ambiguous unlinked orders. | Preserve add and safe delete with confirmation and frontend permission affordance. Do not expose order hard-delete, claim full customer erasure, or delete records by shared phone. | Confirm the target identity and irreversible effect; show server result/error; refresh the list. Explain residual-data/erasure limits where relevant and do not claim that related phone records were removed. |

## P0 / P1 / defer / reject

| Priority | Scope |
|---|---|
| P0 | Search-first Orders list; remove untrusted summary cards; show exact lifecycle/payment/delivery facts; safe detail and canonical booking-confidence actions; distinguish contacts from verified buyers; make RTO consent meaningful before exposing it as an opt-out; do not auto-decline from a phone signal; never dispatch a partial-payment order with an unknown due amount; correct failed-attempt vs final-RTO evidence; protect privacy/tenant boundaries. |
| P1 | Wire explicit custom date bounds if supported; make Orders and Customers search copy match actual query fields; fix stale customer summary display by removing cards or refreshing authoritative totals; provide customer selected-context panel and verified order/conversation links; expose existing notes/tags only with their actual team visibility/permission semantics; accessible error/retry states. |
| DEFER | Settlement/reconciliation views, bank receipt, payment amount ledger, advanced customer segmentation, CRM identity merge, automated outreach, promotional messaging, courier/bulk status actions, channel filtering unsupported by server, per-page state sorting/filtering without authoritative query support, new workflow engine, new database migration. |
| REJECT | Fake `Needs Attention` counts, total counts inferred from the first 100 rows, “delivered = paid/settled”, contact = buyer, phone match = verified person, fake fraud probability, automatic buyer decline from shared-phone signal, dead blacklist routes, unsupported promotional CTA, and hard order deletion in the ordinary worklist. |

## Independent challenge and unresolved expert questions

The expert questions missing from a visual-only redesign are: Which real operator owns each transition? Which search key and filter do they use under time pressure? What makes a courier booking unsafe? What does a merchant think “RTO risk”, “paid”, “delivered”, and “settled” mean? How often is a phone shared? What happens when the provider times out after accepting a booking? How does the team recover from stale data, 403/409, offline connectivity, or a failed settings read? Are the Bangla labels legible on the actual device at normal zoom?

No merchant answers are available yet. Validate those questions through consented task observation before making market-performance claims. A simulated task, screenshot or mocked API is not field evidence.

## Pre-implementation acceptance plan

- Orders: >100 synthetic rows; exact request parameters; name/phone/order-number search; explicit custom range; independent order/delivery/payment filters; no false total; empty shop vs no match; 401/403/409/422/5xx/timeout; retry preserves filters; stale result never appears as fresh; confidence hold and courier timeout/replay recovery.
- Customers: zero records, contact-only record, confirmed exact-ID order, shared/ambiguous phone, missing phone, pilot on/off, partial API failure, no-contactability, authorized delete confirmation, unauthorized action, exact verified conversation/order link, no cross-shop content.
- Risk/finance: failed delivery attempt then retry is not final RTO; duplicate terminal callback counts once; `contribute=false` is excluded from new writes and aggregation; setting load failure displays unavailable; pending non-COD vs COD method/status matrix; partially paid with unknown balance cannot be booked as full-total COD; delivery never becomes settled cash.
- Roles/privacy: owner/admin-only confidence approval and consent changes; ordinary shop role cannot bypass server checks; arbitrary phone enumeration is not offered; no global signal or other-shop order content leaks.
- UI: Chromium and Firefox journey; EN/BN semantic parity; keyboard/focus/dialog return; axe scans; 1440/1366/1280 desktop, 1024/768 tablet, 390/360 mobile, 320 CSS-pixel reflow, 100/125/200% zoom; manual zoom check separate from viewport emulation.
- CI: remove conditional skips from the Orders E2E acceptance path; unexpected mock routes must fail loudly; include Orders E2E in the protected CI workflow. Existing UI E2E suites mock `/api/*` and are not production evidence. Run backend real-PostgreSQL/Redis integration tests for any changed contracts in a uniquely named disposable stack.

## Evidence limits

The repository can prove synthetic UI behavior, API contracts, shop scoping and selected database transitions. It cannot prove real merchant task success, production authenticated UI behavior without an authorized identity, provider collection, bank settlement, risk calibration, shared-phone prevalence, actual customer-data quality, screen-reader usability or real merchant time savings. Current evidence establishes no improvement percentage; measure against the baseline with real operators if available.
